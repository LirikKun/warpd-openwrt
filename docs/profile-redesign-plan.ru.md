# План переработки warpd: профили прокси и Relay

Статус: план, не реализованные возможности. Функциональный код и настройки роутера этим документом не изменяются. Персональные ссылки и ключи в документ не включаются.

## Объём

- Пользовательские профили WARP, MASQUE (QUIC или HTTP/2) и Relay-WARP: создание, редактирование, включение, выключение и удаление нескольких экземпляров.
- Только один WARP при новой установке. Пустой список после явного удаления сохраняется при перезапуске.
- AWG-настройки отдельно для WARP/Relay-WARP; совместимый версионированный пресет по умолчанию, сверенный с поддерживаемыми Mihomo/WarpScout. Настройки сохраняются и не меняются при обновлении зависимости.
- Отдельные ресурсы Relay, работающие также без прокси как мониторинг IP/переактивация.
- Новые цепочки WARP-to-WARP и цепочки с MASQUE не входят в объём. Старые цепочки требуют явной миграционной политики, а не молчаливого удаления.

## Модель и зависимости

Профиль имеет стабильный ID, имя, тип/транспорт, сохранённый enabled, адрес/порт SOCKS, настройки поиска/закрепления, проверки и локальные исключения. Relay-WARP ссылается на Relay по стабильному ID, а не на имя/секретную ссылку.

Relay имеет ID, имя, сохранённый enabled, приватную ссылку, настройки контроля внешнего IP/переактивации и общее состояние активации. Создание Relay-WARP без ресурса с заданной ссылкой запрещается backend. Удаление Relay запрещается при любых связанных профилях, включая выключенные. Проверка зависимости и удаление сериализованы с созданием/перепривязкой профилей.

Фактическое разрешение работы ребёнка = собственный enabled AND enabled родительского Relay. Выключение Relay закрывает связанные слушатели и останавливает его фоновую активность, но не перезаписывает собственные enabled детей. Повторное включение восстанавливает только ранее включённые профили после необходимых проверок. В интерфейсе дети отображаются приостановленными; их переключатели недоступны, удаление разрешено. Состояния переживают перезапуск. Соседние профили не отключаются; применение общего конфига Mihomo может кратковременно повлиять на соединения, что должно быть явно обозначено.

## Исключения: предлагаемая семантика

Глобальные запрещённые страны/ноды дополняются локальными запретами каждого профиля. Итог — объединение без дубликатов. Пустые локальные списки означают наследование глобальных, а не их отмену. Локальные настройки не разрешают глобально запрещённое. Интерфейс показывает эффективный список и источник каждого запрета.

Страны — ISO-коды страны наблюдаемого Cloudflare HTTP-colo; ноды — его коды, например DME/FRA. Не смешивать страну Relay-сервера, страну HTTP-colo и страну публичного выходного IP. География публичного IP проверяется отдельно; исключение страны HTTP-colo не доказывает запрет выходных IP этой страны. Эта семантика должна быть явно названа в форме.

Пример: глобально страны RU и нода DME, локально страны BY и нода FRA => эффективные страны RU,BY; ноды DME,FRA. Это пример семантики, не дополнительный обязательный набор стран по умолчанию.

Фильтры применяются к автоматическому отбору и ручным закреплениям. Передача в WarpScout — по одному объединённому значению каждого флага, не повторённые last-value-wins флаги. Где транспорт/сканер не умеет предварительно фильтровать, необходима проверка кандидата после подключения; неподдерживаемый фильтр нельзя молча игнорировать. Неизвестная география не означает разрешённую. При отсутствии подходящего кандидата — явная недоступность, без ослабления правил или скрытого перехода на прямой WARP. Для запрета реального использования неподходящего выхода требуется реализованное управление слушателем, а не только красный индикатор policy_ready.

Изменение глобальных списков пересчитывает эффективные правила всех профилей. Результаты поиска/health старой ревизии, удалённого или остановленного профиля не применяются. Кэш/дедупликация поиска учитывают эффективные настройки, не только тип WARP/MASQUE.

## Relay и безопасность

- Публичный каталог стран: de/nl/fi/lv/ee.tribukvy.ltd, порт 4500; совместимость туннельного профиля ещё требует проверки по конфигурации провайдера.
- HTTPS-активация выполняется роутером с нужного публичного IP. Никаких Telegram-сессий. Не открывать персональную ссылку с агентского хоста или при офлайн-тестах.
- Ограничить адрес активации и допустимые перенаправления; TLS-проверка обязательна. Ссылку хранить в приватном файле 0600 и не возвращать в статусе, экспорте общих настроек, ошибках, логах или аргументах процессов.
- Проверить согласованный выход HTTPS/UDP и семейство IP с учётом WAN, CGNAT и существующей прозрачной маршрутизации. Отключённый HTTP_PROXY сам по себе не доказывает обход SSClash. Его конфиг, сеть и firewall не меняются.
- Один механизм активации на ресурс Relay; не отдельный цикл на каждый прокси. При одинаковой учётной ссылке и конкурирующих путях выхода нужна защита от взаимных перепривязок.
- Различать наблюдаемый IP, подтверждённую активацию и готовность туннеля. Ошибка IP-сервиса не считается сменой адреса. Использовать ограниченные повторы и cooldown. HTTP 200 сам по себе не доказывает активацию.
- Мониторинг без профилей не требует аккаунта WARP, SOCKS или запуска Mihomo; не заявляет проверенную работоспособность внешнего клиента.
- Локальное выключение Relay не означает отзыв уже существующей привязки у провайдера. Уже отправленное внешнее действие нельзя обещать откатить локальной транзакцией.

## Этапы

1. Зафиксировать схему конфигурации/API, семантику состояний и исключений, миграционный формат; снять безопасную резервную копию перед работами на роутере.
2. Реализовать модель профилей и ресурсов Relay, CRUD, валидацию, атомарное сохранение и правила зависимостей через TDD.
3. Перевести генерацию Mihomo, поиск, проверки, счётчики и журналы на ID профилей. Сохранить один общий движок; отсутствие активных прокси не должно держать его запущенным.
4. Реализовать глобальные/локальные исключения, эффективную политику, версионированные AWG-пресеты и редактирование поддерживаемых параметров.
5. Реализовать защищённую активацию Relay, мониторинг IP и режимы с/без прокси. Первичную внешнюю активацию выполнять только явно и с роутера после подтверждения пути.
6. Переделать русский/английский UI: список прокси и мастер, отдельный Relay-раздел, глобальные настройки, локальные и эффективные исключения, ошибки/ожидание/готовность, подтверждения удаления.
7. Реализовать миграцию и обратимый установочный переход. Сохранить аккаунт, язык, порты, enabled и исключения; не применять свежие defaults поверх существующей конфигурации. Для активной неподдерживаемой цепочки безопасно остановить миграцию с объяснением, не молча отключать её. Неактивные устаревшие данные сохранить для восстановления.
8. Выполнить полную проверку, независимое ревью, сборки ARM64/AMD64, README, commit/push и релиз; отдельно провести согласованную проверку на роутере с подготовленным откатом.

## Критерии приёмки

- Повторные CRUD нескольких одинаковых типов, занятые порты, удаление последнего профиля, сохранение после перезапуска, ошибки записи/применения и отмена устаревших результатов.
- Отсутствие обхода Relay-зависимостей через API; запрет удаления со ссылками; точное восстановление детей и реальное закрытие слушателей.
- Глобальные/локальные фильтры, наследование, нормализация, ручные кандидаты, неизвестная география, изменение правил во время поиска и отсутствие пригодных кандидатов.
- AWG-поля действительно доходят до движка; неподдерживаемые значения отклоняются; значения других профилей не меняются.
- Relay-монитор работает без Mihomo; смена IP/ошибки сети/повторы/выключение/гонки не создают лишних активаций; секреты отсутствуют в публичных поверхностях.
- Go tests/race/vet, офлайн OpenWrt/BusyBox lifecycle/rollback, Node DOM для обоих языков, реальный браузер desktop/mobile light/dark.
- Live-результаты активации и внешнего IP не подменяются фикстурами; если доступ или подтверждение протокола провайдера недоступны, блокер явно указан.
